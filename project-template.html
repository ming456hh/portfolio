核心实现思路与技术亮点

3.1 软件架构设计

软件基于 FreeRTOS 多任务架构，划分为 4 个核心任务：传感器采集任务（高优先级）、数据处理任务、显示刷新任务、通信任务。 任务间通过消息队列传递传感器数据，使用二值信号量同步 OLED 刷新时机。

  • 采集任务优先级最高（prio=3），确保传感器数据不丢帧
  • 显示任务优先级最低（prio=1），利用空闲时间刷新屏幕
  • 使用 FreeRTOS 软件定时器实现 100Hz 周期性采样触发

3.2 FreeRTOS 关键技术点

任务同步 使用二值信号量实现采集完成 → 数据处理 → 显示刷新的流水线同步，避免数据竞争。
消息队列 创建长度为 10 的消息队列缓冲传感器数据，采集任务写入、处理任务读取，解耦采集与处理速率。
内存优化 通过 FreeRTOS heap_4 管理动态内存，总 RAM 占用控制在 15KB 以内，满足 MCU 资源约束。

3.3 通信技术亮点

蓝牙 BLE 自定义 GATT Service，定义 3 个 Characteristic 分别用于数据上报、指令下发和设备状态。手机端通过 nRF Connect 调试验证。
串口协议 设计二进制帧协议：帧头 (0xAA 0x55) + 长度 + 命令字 + 数据 + CRC16 校验，支持可变长度数据包传输。
DMA 传输 UART 收发均使用 DMA + 空闲中断方式，释放 CPU 资源，实测在 115200bps 下 CPU 占用率 < 2%。

遇到的难点与解决方案

难点 1：多任务并发导致的数据竞争

现象：传感器数据偶尔出现乱码或丢失

分析过程：通过逻辑分析仪抓取 I²C 总线时序，发现当显示任务正在读取 OLED 时，采集任务同时触发了传感器读取，导致 I²C 总线仲裁冲突。

解决方案：

  • 引入互斥锁 (Mutex) 保护 I²C 总线访问，确保同一时刻只有一个任务操作总线
  • 将 I²C 操作封装为临界区，在 taskENTER_CRITICAL() 内完成原子操作
  • 优化后连续测试 48 小时无误码

难点 2：蓝牙连接不稳定 / 断连

现象：蓝牙模块在运行一段时间后自动断开，需手动复位

分析过程：抓取 UART 通信日志发现，蓝牙模块在连续接收大量数据时会进入缓存溢出状态，导致模块内部看门狗复位。

解决方案：

  • 在发送端加入流控机制，每次发送后等待 ACK 再发下一帧
  • MCU 端实现蓝牙状态监测任务，心跳超时自动重连
  • 加入硬件流控 (RTS/CTS) 接线

难点 3：实时显示刷新闪烁问题

现象：OLED 屏幕刷新时出现明显闪烁

分析过程：屏幕刷新过程中被其他高优先级任务打断，导致刷屏时序不连续。

解决方案：

  • 使用双缓冲机制 — 在内存中构建完整显存，一次性 DMA 推送到 OLED
  • 将刷屏操作放在空闲钩子函数 (vApplicationIdleHook) 中执行

📄 sensor_task.c — 传感器采集任务
C /* 高优先级传感器采集任务 */ void vSensorTask(void *pvParameters) { SensorData_t xSensorData; TickType_t xLastWakeTime = xTaskGetTickCount(); for (;;) { // 获取 I²C 总线互斥锁 if (xSemaphoreTake(xI2CMutex, pdMS_TO_TICKS(50)) == pdTRUE) { // 读取 BMP280 温湿度 BMP280_ReadData(&xSensorData.temperature, &xSensorData.pressure); // 读取 MPU6050 姿态数据 MPU6050_ReadAccel(&xSensorData.accel_x, &xSensorData.accel_y, &xSensorData.accel_z); xSemaphoreGive(xI2CMutex); } // 发送到消息队列 (非阻塞) xQueueSend(xSensorQueue, &xSensorData, 0); // 精确延时 10ms → 100Hz 采样率 vTaskDelayUntil(&xLastWakeTime, pdMS_TO_TICKS(10)); } }
